# Анализ требований

## Назначение системы

Хранить учебные задачи и помогать планировать их выполнение с учётом сроков, важности, сложности и требуемого времени.

## Целевая аудитория

Студенты, которым нужно самостоятельно планировать домашние, лабораторные, практические и курсовые работы, экзамены и другие учебные дела. Один аккаунт представляет одного студента; ролей преподавателя и администратора в интерфейсе нет.

## Проблема

Задания поступают по разным каналам, сроки теряются, а порядок выполнения выбирается случайно. Общий список с календарём снижает риск забыть работу, а объяснимый приоритет помогает начать с важного.

Система рассчитана на личные учебные списки. Пагинация, массовая нагрузка и промышленное развёртывание не входят в текущую версию; отдельные SLA по скорости не заявляются.

## Основные пользовательские сценарии

### UC-01 Регистрация

- Актор: новый студент.
- Предусловие: открыт экран регистрации, API и БД доступны.
- Основной сценарий: студент вводит имя, email, пароль → frontend отправляет запрос → сервер проверяет данные и уникальность email → хэширует пароль → создаёт пользователя → возвращает JWT → открывается Dashboard.
- Результат: создан личный аккаунт с пустым учебным планом.
- Альтернатива: неверные поля или существующий email отображаются в форме; аккаунт не создаётся.

### UC-02 Авторизация

- Актор: зарегистрированный студент.
- Предусловие: существует аккаунт.
- Основной сценарий: ввод email и пароля → сравнение bcrypt → получение JWT → сохранение в sessionStorage → Dashboard или исходно запрошенная страница.
- Результат: доступны собственные данные.
- Альтернатива: при неверных данных показана общая ошибка; при истёкшем токене требуется повторный вход.

### UC-03 Создание задачи

- Актор: авторизованный студент.
- Предусловие: создан хотя бы один предмет.
- Основной сценарий: «Новая задача» → заполнение обязательных полей → «Сохранить задачу» → проверка владельца предмета и валидация → INSERT в PostgreSQL → уведомление → список задач.
- Результат: задача сохранена и участвует в списке, календаре, статистике и рекомендации, если не завершена.
- Альтернатива: без предметов показан переход к их созданию; ошибки формы не приводят к сохранению.

### UC-04 Редактирование задачи

- Актор: владелец задачи.
- Предусловие: задача существует.
- Основной сценарий: открыть редактирование → изменить параметры → сохранить → сервер проверяет владельца и обновляет запись → следующий запрос пересчитывает приоритет.
- Результат: новые значения сохранены; completedAt согласован со статусом.
- Альтернатива: чужой ID возвращает 404, чужой предмет не может быть выбран для записи.

### UC-05 Удаление задачи

- Актор: владелец задачи.
- Предусловие: задача видна в списке или открыта.
- Основной сценарий: «Удалить» → диалог подтверждения → подтверждение → DELETE → обновление списка.
- Результат: задача удалена из БД, календаря, рекомендации и отчётов.
- Альтернатива: «Отмена» или Escape оставляют запись без изменений.

### UC-06 Завершение задачи

- Актор: владелец задачи.
- Предусловие: задача незавершённая.
- Основной сценарий: «Выполнено» → PATCH → status=completed, completedAt=now → обновление UI.
- Результат: задача не просрочена и не рекомендуется, увеличивается количество выполненных.
- Альтернатива: повторный запрос не меняет исходное время завершения; через редактирование можно вернуть задачу в работу.

### UC-07 Просмотр дедлайнов

- Актор: авторизованный студент.
- Предусловие: открыт Dashboard или календарь.
- Основной сценарий: просмотреть ближайшие задачи → открыть календарь → выбрать месяц → нажать на задачу.
- Результат: открыта карточка задачи со сроком, описанием и действиями.
- Альтернатива: пустые дни остаются пустыми; выполненные задачи в календаре отмечены галочкой.

### UC-08 Получение рекомендации

- Актор: авторизованный студент.
- Предусловие: есть незавершённые задачи.
- Основной сценарий: открыть Dashboard → сервер рассчитывает score по пяти факторам → выбирает максимум → отображает задачу и объяснение.
- Результат: студент видит обоснованный следующий шаг.
- Альтернатива: при отсутствии задач предложено создать первую, при завершении всех — сообщение «Всё выполнено!».

### UC-09 Управление предметами

- Актор: авторизованный студент.
- Предусловие: открыта страница «Предметы».
- Основной сценарий: добавить название, преподавателя и цвет → сохранить → при необходимости отредактировать → удалить с подтверждением.
- Результат: собственные предметы доступны в форме задачи; выбранный цвет отображается в карточках и календаре.
- Альтернатива: дубликат имени запрещён; удаление предмета с задачами возвращает сообщение о необходимости переноса или удаления задач.
